# Interactive ABC Score node

Status: ready-for-agent

## Problem Statement

ComfyUI has no way to work with sheet music. A user who wants a tune — written by hand, transcribed by a model, or generated by an LLM as ABC notation — has to leave ComfyUI, paste the ABC text into a website such as editor.drawthedots.com, look at the notation there, listen to it there, tweak it there, and then copy the text back by hand. There is no node that shows the score, plays it, lets the user change it, and hands the resulting ABC text back to the rest of the graph.

The user's stated wish is stronger than "a text box with a preview": they want to **edit the music on the sheet itself**, because clicking a note and moving it is easier than finding that note in a wall of ABC characters.

## Solution

One ComfyUI node — **ABC Score** — that is simultaneously a score editor, a player, and a text producer.

- The node shows the score rendered from ABC notation and plays it (play / pause / loop / restart / seek / tempo) without leaving the graph.
- Editing is score-first: click a note to hear it and select it, then change it with the keyboard (pitch, duration, accidental, rest, delete) or by dragging it on the staff. Every gesture rewrites the underlying ABC text and re-renders. A collapsible ABC text pane stays available for pasting and expert edits.
- The ABC text is a normal ComfyUI string: it can arrive from any existing text node (Text Multiline, an LLM output, Concatenate Text) and it leaves as a string output that any string-consuming node can use. Editing the upstream text node updates the score live.
- Everything renders and sounds offline. Nothing in the node talks to the internet.

## User Stories

1. As a workflow author, I want a node that renders ABC notation as sheet music inside the graph, so that I can see the music I am producing without leaving ComfyUI.
2. As a workflow author, I want to connect an existing text node to the ABC Score node, so that any text I already produce becomes a score.
3. As a workflow author, I want to type ABC notation into an upstream Text Multiline node and watch the score update, so that I do not have to re-queue a graph just to preview a change.
4. As a workflow author, I want the node to output the ABC notation as a string, so that I can feed the score to other nodes — a text file writer, a prompt, a comparison, another model.
5. As a musician, I want to click a note on the staff and hear just that note, so that I can identify what I am looking at before I change it.
6. As a musician, I want the clicked note's position in the ABC text to become the selection, so that the score and the text always agree about what "this note" is.
7. As a musician, I want to change a selected note's pitch with the up/down arrow keys, so that I can fix a wrong note in one keystroke.
8. As a musician, I want to lengthen and shorten a selected note, so that I can fix rhythm without counting characters.
9. As a musician, I want to add, remove, and toggle sharps, flats, and naturals on a selected note, so that I can fix accidentals without remembering ABC syntax.
10. As a musician, I want to turn a selected note into a rest and back, so that I can silence a note quickly.
11. As a musician, I want to delete a selected note or rest, so that I can shorten a phrase.
12. As a musician, I want to insert a note or rest after the selection, so that I can extend a phrase without editing raw text.
13. As a musician, I want to drag a note up and down the staff, so that I can set its pitch by ear and by eye instead of by keystrokes.
14. As a musician, I want to select bars, key signatures, time signatures, titles, tempos, and lyrics, so that the things I most often need to change are reachable from the sheet too.
15. As a musician, I want playback to highlight the note currently sounding, so that I can follow the score while it plays.
16. As a musician, I want to loop a passage while I work on it, so that I can hear a fix repeatedly without reaching for the play button.
17. As a musician, I want to change the tempo during playback, so that I can check a fast passage slowly.
18. As a musician, I want to seek to any point in the tune, so that I can jump to the bar I am editing.
19. As a workflow author, I want Ctrl+Z and Ctrl+Shift+Z to undo and redo score edits, so that I can experiment with note changes without fear.
20. As a workflow author, I want the current score to be saved in the workflow, so that reopening the workflow brings back the exact music I wrote.
21. As a workflow author, I want a warning shown when the ABC text does not parse, pointing at the offending line, so that a typo produces a message instead of silence or a blank node.
22. As a workflow author, I want the node to keep showing the last good score when my latest text is broken, so that a half-typed bar does not destroy my work in progress.
23. As a workflow author, I want to collapse the score, the text pane, or the player independently, so that the node fits the space I have and the graph stays readable.
24. As a workflow author, I want to resize the node, so that a long tune is legible without scrolling horizontally.
25. As a workflow author, I want to know at a glance whether the score comes from the node itself or from a linked text node, so that I am never unsure which text my output carries.
26. As a workflow author, I want a one-click way to break the link and keep the currently displayed score as the node's own text, so that I can refine a generated tune without editing the upstream node.
27. As a workflow author working with a generated tune, I want a multi-tune ABC string to render and play in full, so that a model returning several tunes still works.
28. As a workflow author, I want an edit inside one tune of a multi-tune string to leave the other tunes byte-for-byte untouched, so that editing does not corrupt the rest of the artifact.
29. As a workflow author, I want to transpose the whole tune by a number of semitones, so that I can move a generated melody into a usable key.
30. As a keyboard-only user, I want to move the selection with Tab and the arrow keys, so that I can edit a score without a mouse.
31. As an offline user, I want the score to render and the audio to play with no network access, so that the node works on a machine that is not connected.
32. As a user on a constrained machine, I want the editor to stop doing work while the node is collapsed, off-screen, or zoomed far out, so that a graph full of these nodes does not chew through CPU.
33. As a workflow author, I want an empty node to start from a short playable example tune, so that I understand what the node does the moment I add it.
34. As a workflow author, I want the string output to update as I edit, without needing an extra "commit" step, so that the score I see is the score downstream nodes receive.
35. As a workflow author, I want the node to pass text through unchanged, so that my formatting, line breaks, and comments survive a round trip.

## Implementation Decisions

### Node contract (backend)

- One node, `ABC Score`, with one input and one output:
  - Input `abc`: string, multiline, linkable, with a default example tune. It is both a socket (accepts any string-producing node) and a widget (holds the node's own score when nothing is linked).
  - Output: a single string — the ABC score.
- The Python side is a **pure text carrier**: no ABC parsing, no validation, no normalisation, no reformatting, no whitespace cleanup. Whatever text is effective is emitted verbatim. Rendering, parsing, warnings, and editing all live in the browser. This keeps the backend trivial, keeps behaviour identical between the editor and the graph, and avoids a second ABC implementation in Python.
- Precedence rule: **a linked input wins**. When `abc` is linked, the upstream string is what flows to the output; the node's own stored widget text is ignored. This is standard ComfyUI behaviour and must not be subverted.
- Registered through the current custom-node entry points (`NODE_CLASS_MAPPINGS` / `NODE_DISPLAY_NAME_MAPPINGS`, plus the frontend static directory), so the node behaves like any other extension node with respect to loading, workflow serialisation, and prompt validation.
- The node package adds nothing to the parent ComfyUI install: no new dependencies in the core requirements, no core file touched.

### Where the interactive surface lives

- A browser-side extension of this node package. The ABC text widget is replaced by a custom widget that mounts a DOM layer inside the node; the node sizes itself around it and the DOM layer is mapped onto the node's on-screen rectangle so it moves, scales, and clips with the graph.
- The widget's value is the canonical ABC string and uses normal widget serialisation, so scores persist in workflows, copy/paste, and the prompt payload.
- Three panes in the node: the score, the collapsible ABC text pane, and the player controls. Collapsed panes render nothing and subscribe to nothing.

### Rendering and playback

- Use abcjs as the single renderer, parser, and synth. It is vendored into the node package and served by ComfyUI from the node's own static route (`/extensions/<package name>/…`); it is not loaded from a CDN and nothing in this node makes an internet request at runtime.
- Reuse abcjs's editor wiring rather than rebuilding it: it already gives instant text-to-notation update, a warnings channel, and a player with play/pause, loop, restart, progress seek, and warp (tempo).
- Playback uses abcjs's SoundFont synth. A SoundFont is required for audio, so one General-MIDI instrument set is vendored locally (~2 MB, per-instrument folders in the standard `midi-js-soundfonts` layout) and the synth is pointed at the local static route. A configurable SoundFont root lets a user who wants the full multi-instrument set drop it in locally; the default install must never reach for the network.
- The Web Audio context is created only after the first user gesture, as browsers require; the player shows a "click to enable audio" affordance until then.
- A cursor animation highlights the sounding note during playback, matching the reference site's "red notes follow the score" behaviour.
- Re-render is debounced (a couple of hundred milliseconds) and re-primes audio only when the text actually changed. Nothing re-renders while the node is collapsed, off-screen, or below a zoom threshold.

### Score-first editing

- Rendering turns on abcjs's click listener and dragging, with selectable element types restricted to musical things: notes and rests, bars, key signature, time signature, clef, title, subtitle, tempo, part names, dynamic decorations, slurs, and lyrics.
- **abcjs never mutates the ABC text.** Every gesture produces only a description of what was touched — the character span of the element in the original string, and for a drag a signed count of visual staff steps. All mutation is done by this node's own edit model, then re-rendered.
- Every gesture, mouse or keyboard, is expressed as a small structured edit operation applied to the string. The shape, settled during the design discussion and prototyping:

  ```js
  edit(abc, selection, op) -> { abc, selection }

  selection = { startChar, endChar }

  op = { kind: 'pitch',   steps }              // arrow keys: diatonic staff steps
     | { kind: 'drag',    steps }              // drag result, visual staff steps
     | { kind: 'duration', direction }         // '<' shorten / '>' lengthen
     | { kind: 'accidental', accidental }      // sharp | flat | natural | none
     | { kind: 'to-rest' }
     | { kind: 'insert', after, what }         // note (copy of selection) or rest
     | { kind: 'delete' }
  ```

  Operations address the tune containing the selection and never touch text outside it, which is what makes a multi-tune string safe to edit.
- Keyboard: arrows for pitch, dedicated keys for shorten/lengthen, accidental add/remove, rest toggle, delete, and insert. Keys are bound only while the score has focus, so they never swallow keystrokes meant for a text widget elsewhere in the graph.
- Selection is character offsets, not object references, so it is re-established after every re-render and survives text that shifts.
- Undo/redo is an in-memory stack of complete ABC strings per node, capped in length, cleared when the node's text is replaced by a link or a workflow load. Full-string snapshots are deliberate: they are simple, correct for multi-tune strings, and cheap at tune sizes.
- Transpose reuses abcjs's own string transposition so the ABC text itself is rewritten (not just visually transposed), because the output string is the product.
- The ABC text pane and the score are two views of one string: typing in the pane re-renders the score; editing the score rewrites the pane.

### Keeping the linked text and the score in step

- Live mirror: when `abc` is linked, the editor subscribes to value changes on the linked origin node's widget and re-renders, so typing in a Text Multiline node updates the score without queueing anything.
- Authoritative mirror: on each execution the node reports the effective text through the standard text-preview UI channel and the editor adopts it. Live mirroring is best-effort; the execution echo guarantees they can never drift for long.
- While linked, the score still plays and clicking still selects and sounds notes, but string-mutating gestures are refused with an inline hint rather than silently doing nothing. A "detach and edit" control converts the input to a widget (ComfyUI's own input-to-widget action) so the displayed score becomes the node's own text and the edits stick.
- The node header states the source: `ABC Score — from: <upstream node title>` versus `ABC Score — self`.

### Failure behaviour

- Parse problems go to the abcjs warnings pane, short and pointing at the line. A string that renders nothing at all shows a one-line "no tune found" note instead of an empty box.
- A bad edit that would produce unparseable text is not special-cased: the text is written, the warning pane complains, and undo is available. Refusing edits on principle is out of scope — a bad score is better than a blocked workflow, and the user can always undo.

## Testing Decisions

Good tests here assert **strings in, strings out**. They never touch the DOM, never load abcjs, never open a browser, and never assert on internal helper calls. The parse offsets an edit needs are supplied as plain data by the test, exactly as the click listener supplies them in the app.

Two seams, both new, both as high as they can go.

1. **Score-edit model** — the primary seam, and the only place with real logic. A pure browser-free module mapping `(abc string, selection, edit op) -> { abc, selection }`. All mouse, keyboard, and drag gestures funnel through it, so the app layer stays thin enough to leave untested. Run with the Node built-in test runner: no bundler, no build step, no dependency on ComfyUI. Fixtures are short hand-written ABC scores. Cases to cover:
   - pitch up/down, including crossing octave boundaries, key-signature accidentals, and the ends of the usable range;
   - duration shorten/lengthen on plain, dotted, and beamed notes; tuplets get defined best-effort behaviour, not a crash;
   - accidental add, replace, remove, and no-op when already in that state;
   - note to rest and back; delete note; delete rest; insert after selection;
   - drag with `step` 0, positive, negative;
   - multi-tune strings: an edit inside tune two leaves tune one byte-identical;
   - header lines, lyric lines, field lines, comments, and trailing whitespace are never disturbed;
   - selection offsets that come back pointing at the wrong thing after a rewrite are handled, not trusted.
2. **Node text contract** — a thin Python test that imports the node module and calls the node class directly, no ComfyUI server and no execution engine: unlinked input emits the node's own text verbatim; a linked input wins over the stored widget text; a multi-tune string and unusual whitespace pass through untouched; the output arity and types stay one string. This mirrors how core ComfyUI tests its text nodes under `tests-unit/comfy_extras_test`.

Manual QA checklist, run once against a real ComfyUI, not automated — driving a browser plus a real AudioContext is not worth the harness: render, play/pause/loop/seek/tempo, click-to-hear, drag a note, undo, upstream text node changes the score live, detach-and-edit keeps the score, workflow save/reload restores the score, and everything still works with the network disabled.

Not tested: abcjs's own rendering or synth correctness, SoundFont asset contents, audio latency, and anything about how the DOM overlay sits on the node.

## Out of Scope

- Server-side ABC parsing, validation, conversion, or any Python ABC library.
- Audio output as a ComfyUI artifact: WAV export, MIDI file export, an audio output node, or generating a file on disk. Playback is browser-only.
- Creating new music: no click-on-empty-staff-to-add-a-note, no drag-to-draw, no bar insertion or deletion, no composing from a palette. v1 edits what the text already contains.
- Layout and engraving controls: page size, staff spacing, fonts, scaling options, tablature, chord grids, transpose-by-clef, or part extraction.
- Score formats other than ABC: no MusicXML, MIDI, or LeadSheet import or export.
- Multi-score management, tune libraries, versioning, share links, or persistence beyond the workflow file.
- Any UI or storage for the full multi-instrument SoundFont set — the configuration point exists, the UI does not.
- Collaborative or multiplayer editing, and touch/stylus input.
- Any change, hook, or new dependency in the parent ComfyUI core.

## Further Notes

- Reference behaviour: editor.drawthedots.com (abcjs's own editor app — click-a-note-to-select-and-hear, plus the player) and the interactive ABC score on map-yue2.github.io (playback cursor following the score). The plan matches the first and adds real string-mutating visual editing, which neither site does: there, dragging a note is purely visual and the reference site relies on the user typing in the text pane. That string rewrite is exactly the piece this spec puts behind a test seam.
- abcjs is MIT-licensed and vendored; the General-MIDI SoundFont folders carry their own upstream MIT notice and must keep it in place. Vendored assets should be recorded (source URL and version) so a later refresh is possible.
- The one thing most likely to hurt is the interaction between the widget value, the linked input, and the mirror. If live mirroring turns out to be unreliable on some source node type, drop it and keep the execution echo — correctness over liveness, and the detach path always works.
- Node name, category, and socket labels should follow local ComfyUI conventions (`INPUT_TYPES`, `RETURN_TYPES`, `CATEGORY`, local registration mapping) and stay consistent with the existing text nodes so the node is discoverable next to them.
